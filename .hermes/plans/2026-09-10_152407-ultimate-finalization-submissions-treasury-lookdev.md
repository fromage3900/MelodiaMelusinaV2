## §2 Decisions taken

### #1 — The 9 rejected plates: **retire the weak, replace only what a slot leans on**
Correct and cheapest-honest. `content/render-passports.json` carries 30 entries (16 accepted,
**9 reject**, 5 supporting). Method: for each reject entry either replace with a freshly captured,
pixel-reviewed plate → `accepted`; or downgrade to `supporting` with an honest `does_not_prove` list;
or retire the slot and repoint its consumer in `content/site-plates.json`. The plate file's own
`notes` field already records prior retirements — append to that convention, never overwrite it.
**No entry leaves the file without a status.**

### #2 — New viewer models: **neither option as posed — use `generated/optimized/curated-art/`**

This is the decision the evidence forced. `wix/models/` is **not** covered by the freeze's
`allowed_prefixes` (which are exactly: `generated/assets/character/`, `generated/assets/unreal/`,
`generated/optimized/curated-art/`, `tools/fromage-webgl-kit/`). Writing new models into `wix/models/`
would require a freeze exception; `generated/optimized/curated-art/` requires none and is already an
allowed prefix.

**Decision:** new viewer assets land in `generated/optimized/curated-art/` as **glTF/GLB**, and the
already-allowlisted `wix/melodia-3d-viewport.js` references them. No freeze exception, no new page,
no renderer change.

**Finding surfaced while answering this:** `wix/models/` currently holds **27 files / 298 MB**, of
which **11 × .fbx and 11 × .obj**, plus 5 × .glb. That directory is served by GitHub Pages. The
largest single files are `SM_MelodyToken_Water.fbx` (~90 MB), `SM_MelodyToken_Star.fbx` (~80 MB) and
`SK_Melusina_FullRig_Production.fbx` (~79 MB).

**Before calling this a defect, one question (see §7):** if those FBX files are deliberate
"download my rig" artifacts for recruiters, they are a *serving-strategy* problem, not junk. If they
are leftovers from the viewer's build, they are dead weight in a published directory. Do not delete
either way — this is a freeze-bound path and the answer decides the fix.

### #3 — Melusina B2 hero: **the MRQ/driver path, pointed at the dressed level**

Read from source, not guessed. `deploy/portfolio_render.ps1` invokes
`Content/Python/run_portfolio_capture.py` headlessly, which loads **one level per run** — chosen by
`PORTFOLIO_CAPTURE_LEVEL`, defaulting to `/Game/EnvSandbox/Environments/Sakura/L_SakuraPath` — then
runs `render_exporter` followed by `scene_metadata_exporter`. It is a per-level capture driver, not a
multi-shot hero rig.

The two `SceneCapture2D` actors in `LV_SeaAbove_Prototype` (committed today, `78ce468b`) are **level
dressing, not a capture system**. They do not drive the portfolio capture.

**So it is not either/or.** The canonical B2 hero/portrait capture is:

```
PORTFOLIO_CAPTURE_LEVEL=<the level where Melusina V2 is dressed> ./deploy/portfolio_render.ps1
```

with the two SceneCapture2D actors providing whatever framing they were placed for *inside that
level*. Note the default level is Sakura — to shoot Melusina as she stands today, set the env var to
the Sea Above prototype level explicitly, or the run will render Sakura and produce all-null metadata
for her (this exact silent no-op class is documented in the script's own header comment).
