# Forced Quill dialog presentation during interpreter startup

The change validates and retains the active Quill interpreter, then forces its managed dialog into the viewport, schedules dialog/selection visibility, and forces the mouse cursor on when Quill announces startup. This callback runs after Quill applies the script’s “during” input settings and creates managed widgets, but before the first statement executes. **Watch for:** **[High, likely]** delayed `Show()` callbacks can outlive an interpreter that ends during startup; **[Medium, confirmed]** `ShowMouseCursor()` overrides script cursor policy; **[Medium, confirmed]** `ShowDialogBox()` can present an empty dialog before any dialogue executes.

## High-level view

Quill broadcasts `OnScriptPlay` after `ApplyScriptSettingsDuring()` and widget creation but before `Play()` begins. The dialog pointer is available at this boundary, yet attaching it here is earlier than dialogue presentation and can expose an uninitialized widget for scripts beginning with commands, labels, or battle notifications.

`Show()` installs two next-tick callbacks capturing the interpreter and only then changes dialog and selection visibility. Initial script execution can synchronously end and destroy the interpreter before those callbacks run.

Quill has already resolved and applied cursor visibility, input enablement, and input mode when the new cursor call runs. Battle pause/resume uses `Stop()`/`Restore()` rather than Quill’s sleep/wakeup input lifecycle, so the forced cursor also remains through battle unless another system changes it.

1. **[High, likely] Startup visibility callback can outlive the interpreter** — `Show()` schedules raw-`this` work for two ticks later while initial execution can synchronously destroy the interpreter. Remove this call; if delayed visibility is required, make Quill’s callback weak-pointer-safe.
2. **[Medium, confirmed] Script cursor setting is overridden** — `ShowMouseCursor()` runs after Quill applies `ShowMouseCursorDuring`, forcing hidden-cursor scripts visible and leaving cursor/input mode potentially inconsistent. Remove the unconditional call and let script settings own cursor state.
3. **[Medium, confirmed] Dialog is attached before dialogue presentation** — `ShowDialogBox()` adds the freshly created widget before the first statement, so non-dialogue starts can display an empty dialog. Move attachment into the managed dialogue presentation path or the dialog Blueprint’s `Play()` implementation.

## Delayed visibility crosses synchronous script teardown

**[High, likely]** `HandleQuillScriptPlay()` calls `Show()` at `MelodiaNarrativeSubsystem.cpp:300`. Quill’s implementation schedules nested next-tick lambdas that capture raw `this`. Immediately after `OnScriptPlay` returns, `Start_Implementation()` starts interpreting; an empty script, command-only route, invalid starting label, or another synchronously terminating path can reach `End()`/`Kill()`, reset widgets, and destroy the actor before either timer fires. Unreal’s deferred destruction may affect how this manifests, but neither callback has a validity guard, so the new call creates a credible crash or stale-object access path.

`Show()` is unnecessary for viewport attachment because `ShowDialogBox()` performs that synchronously. The smallest safe correction is to remove `Interpreter->Show()`. A widget that deliberately starts collapsed should reveal itself from the dialogue presentation path, or Quill’s delayed implementation must capture a `TWeakObjectPtr` and validate it on each tick.

## Cursor ownership conflicts with script settings and battle pause

**[Medium, confirmed]** `ShowMouseCursor()` at `MelodiaNarrativeSubsystem.cpp:301` executes after Quill’s `ApplyScriptSettingsDuring()`. It writes `PlayerController->bShowMouseCursor = true` even when the effective `ShowMouseCursorDuring` setting is false, without coordinating `InputModeDuring` or input enablement. This can leave a visible cursor in GameOnly mode or while player input is disabled.

`StartBattle()` only calls `Stop()`, which prevents progression but does not hide UI or apply “after” input settings. Completion and abort call `Restore()` then `Next()`, which do not reapply “during” settings. **[Medium, confirmed]** the forced cursor therefore persists through battle unless unrelated battle code changes it, and normal “after” settings are not applied until the script ends. Remove the cursor call. A battle-specific input/UI handoff, if required, should be an explicit paired lifecycle change rather than startup behavior.

## Dialog attachment precedes the behavior it represents

At broadcast time, native Quill has already called `CreateDialogBox()`, so `ShowDialogBox()` finds a managed widget when management is enabled and a class exists; it is a no-op otherwise. It does not create or initialize a missing dialog, making the new log diagnostic rather than recovery.

**[Medium, confirmed]** adding the widget at startup occurs before `PlayDialogueBox()` calls `Setup()` and `Play()`. Scripts that begin with commands, labels, checkpoints, a battle notification, or terminate without dialogue can therefore show a default or empty dialog. The smallest correction that preserves the intended UI guarantee is to remove the startup attachment and have the configured dialog Blueprint call `AddToViewportAtLayer()` from its `Play()` override. If this must be enforced in native Quill, add `ShowDialogBox()` to the managed `PlayDialogueBox()` path after setup rather than to `OnScriptPlay`.

## Focused verification gaps

No changed tests accompany this callback. Verify a script with `ShowMouseCursorDuring = false`, synchronous termination before two ticks, managed dialogue disabled, a missing dialog class, a non-dialogue first statement, and battle completion/abort while narrative UI is active. The cursor-policy and synchronous-termination cases gate this change.
